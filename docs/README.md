# Процесс Документации

Этот каталог задаёт рабочую модель проекта для долгой разработки с участием LLM и людей.

## Зачем это нужно

Цель в том, чтобы уменьшить четыре класса проблем:

1. дублирование логики
2. расхождение стиля и архитектурных решений
3. появление заглушек вместо полноценной реализации
4. дорогая отладка из-за незафиксированных договорённостей

## Основные документы

- `constitution.md` фиксирует правила проекта
- `architecture.md` описывает текущее устройство системы
- `devplan.md` хранит среднесрочные этапы развития
- `adr/` хранит долгоживущие технические решения
- `tasks/` хранит спецификации задач

## Обязательный процесс работы

1. Начинать с task spec в `docs/tasks/`.
2. Если задача меняет архитектуру или вводит долгоживущий компромисс, добавлять или обновлять ADR.
3. Если задача меняет границы системы, обновлять `architecture.md`.
4. Реализовывать только то, что входит в утверждённый scope задачи.
5. Выполнять шаги verification, перечисленные в задаче.
6. Если остаётся продолжение работы, создавать новую задачу, а не оставлять скрытый технический долг.

## Когда создавать ADR

Создавайте ADR, если задача меняет:

- стратегию хранения данных
- модель деплоя
- подход к аутентификации или авторизации
- стратегию API-контрактов
- source of truth для расписания или записи
- границу между Telegram-ботом и backend Mini App

## Definition of Done

Задача считается завершённой только если:

- acceptance criteria выполнены
- verification выполнен или явно заблокирован
- документация обновлена, если поменялось поведение или архитектура
- в production-потоке не осталось скрытых заглушек или временных веток логики
