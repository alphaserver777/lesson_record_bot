# Процесс Документации

Этот каталог задаёт рабочую модель проекта для долгой разработки с участием LLM и людей.

## Зачем это нужно

Цель в том, чтобы уменьшить четыре класса проблем:

1. дублирование логики
2. расхождение стиля и архитектурных решений
3. появление заглушек вместо полноценной реализации
4. дорогая отладка из-за незафиксированных договорённостей

## Основные документы

- `DEPLOYMENT.md` описывает production deployment и rollback
- `constitution.md` фиксирует правила проекта
- `architecture.md` описывает текущее устройство системы
- `devplan.md` хранит среднесрочные этапы развития
- `adr/` хранит долгоживущие технические решения
- `tasks/` хранит спецификации задач

## Важный операционный факт

Если изменение затрагивает Telegram Mini App, backend Mini App или их deployment, нужно учитывать текущее production-размещение:

- сервер: `Germany2.play2go.cloud`
- контейнер backend: `bot_service_appointment_miniapi_prod`
- контейнер frontend: `bot_service_appointment_miniapp_front_prod`
- контейнер основного бота: `bot_service_appointment_prod`

## Обязательный процесс работы

1. Перед написанием новой задачи или началом реализации перечитывать актуальные документы проекта:
   `docs/WORKFLOW.md`, `docs/constitution.md`, `docs/architecture.md`, `docs/devplan.md` и релевантные ADR/task specs.
2. Начинать с task spec в `docs/tasks/`.
3. Если задача меняет архитектуру или вводит долгоживущий компромисс, добавлять или обновлять ADR.
4. Если задача меняет границы системы, обновлять `architecture.md`.
5. Реализовывать только то, что входит в утверждённый scope задачи.
6. Выполнять шаги verification, перечисленные в задаче.
7. Если остаётся продолжение работы, создавать новую задачу, а не оставлять скрытый технический долг.

## Когда создавать ADR

Создавайте ADR, если задача меняет:

- стратегию хранения данных
- модель деплоя
- подход к аутентификации или авторизации
- стратегию API-контрактов
- source of truth для расписания или записи
- границу между Telegram-ботом и backend Mini App

## Definition of Done

Задача считается завершённой только если:

- acceptance criteria выполнены
- verification выполнен или явно заблокирован
- документация обновлена, если поменялось поведение или архитектура
- в production-потоке не осталось скрытых заглушек или временных веток логики
