# Task: admin-miniapp-blocks

## Status

Done

## Контекст

Сейчас в проекте уже существует логика административной блокировки времени через legacy Telegram-бот. Она находится в `handlers/custom_handlers/actions_with_admin/reserve_day.py` и частично опирается на `database/transactions.py`.

При этом в текущем Mini App для администратора в разделе календаря есть режим `Заявки`, хотя согласование заявок уже устраивает в Telegram-боте через inline-кнопки и не требует отдельного frontend-потока.

Дополнительно текущая логика резерва в backend неполная:

- в интерфейсе legacy-бота есть ввод диапазона времени
- но `transactions.reserve_day(...)` фактически создаёт только full-day block special case
- в Mini App отсутствует UI для создания административной брони дня или периода внутри дня

Это создаёт разрыв между реальной операционной задачей и доступным интерфейсом администратора.

## Цель

Заменить режим `Заявки` в административном Mini App на режим `Бронь`, в котором администратор может:

- забронировать весь конкретный день
- забронировать конкретный диапазон времени внутри выбранного дня
- видеть уже созданные блоки на выбранную дату
- удалять созданные блоки
- выбрать сценарий обработки уже существующих занятий, если они пересекаются с новым блоком

Согласование заявок при этом полностью остаётся в Telegram-боте и убирается из frontend Mini App.

## Scope

В scope:

- убрать frontend-режим `Заявки` из admin Mini App
- добавить frontend-режим `Бронь` в календаре администратора
- добавить backend API для просмотра, создания и удаления блоков на день
- реализовать блокировку на конкретный день и на период внутри дня
- использовать рабочее расписание как базовую рамку доступного времени
- показывать существующие блоки в читаемом виде на выбранный день
- поддержать сценарий отмены пересекающихся занятий с уведомлением ученикам

Вне scope:

- перенос логики согласования заявок из Telegram-бота
- периодические блоки по дням недели или по шаблону
- автоматическая отмена существующих записей, попавших в блок
- переработка общего UX всех административных вкладок
- миграция с SQLite на другую БД

## Ограничения

- Рабочее расписание остаётся основой доступного времени: блок можно ставить только на конкретную дату, а не как повторяющееся правило.
- Блоки не должны ломать существующую логику расчёта свободных слотов для пользователей.
- Существующие записи не должны удаляться автоматически без явного выбора администратора.
- Новая логика должна по возможности опираться на уже существующую модель `RecordDate.kind = "block"`, без введения лишней сущности.
- Нужно минимизировать special cases, связанные с full-day block.
- Уведомления об отмене должны быть шаблонными или редактируемыми вручную, но не должны требовать отдельного сложного редактора.

## Текущее состояние

- Во frontend admin Mini App в календаре есть режимы `Записанные / Свободные слоты / Заявки`.
- Pending approvals во frontend грузятся отдельно и управляются через Mini App.
- В Telegram-боте already exists flow для согласования заявок.
- В БД и backend уже используются block-записи, которые влияют на отображение расписания и доступность слотов.
- Отображение block-записей на день для администратора уже частично реализовано в `/api/admin/schedule/day`.

## Предлагаемое изменение

### 1. Frontend

В admin Mini App:

- заменить сегмент `Заявки` на `Бронь`
- убрать карточки списка и деталей заявок на согласование
- добавить экран бронирования на выбранный день

Экран `Бронь` должен включать:

- список текущих блоков на выбранную дату
- действие `Забронировать весь день`
- форму брони периода:
  - дата берётся из выбранного дня в календаре
  - время начала
  - время окончания
  - комментарий
- возможность удалить отдельную бронь

Если новый блок пересекается с существующими занятиями, перед подтверждением должно появляться модальное окно или confirm-panel с выбором сценария:

- просто заблокировать время
- заблокировать и отменить пересекающиеся занятия с уведомлением

Если выбран сценарий с отменой и уведомлением, администратору должно быть доступно:

- выбрать шаблон причины:
  - `Заболел`
  - `Срочная командировка`
  - `Форс-мажор`
- или ввести свой текст вручную

### 2. Backend API

Добавить admin endpoints для блоков:

- получение блоков на дату
- создание full-day block на дату
- создание period block на дату с временем начала и окончания
- удаление блока или диапазона блоков на дату
- preview пересечений нового блока с существующими занятиями
- создание блока с выбранной conflict-strategy:
  - только блокировка
  - блокировка + отмена занятий + уведомление

### 3. Доменная модель

Рабочее расписание остаётся базовой рамкой.

Блок:

- относится только к конкретной дате
- может перекрывать весь день в рамках рабочего графика
- может перекрывать только часть дня

Хранение:

- использовать существующую модель `RecordDate.kind = "block"`
- full-day block и period block хранить единообразно как набор block-слотов на конкретную дату
- не использовать отдельную повторяющуюся сущность для блокировок

### 4. Поведение при конфликтах

Если внутри выбранного диапазона уже есть существующие записи, перед финальным созданием блока администратор должен выбрать одну из стратегий:

- `block_only`: блок создаётся, существующие занятия сохраняются, новое время становится недоступным только для будущих записей
- `block_and_cancel_notify`: блок создаётся, пересекающиеся занятия отменяются, ученикам отправляется уведомление

Уведомление должно поддерживать:

- шаблонные причины
- собственный текст администратора

При стратегии `block_and_cancel_notify`:

- отменяются только пересекающиеся занятия
- уведомление отправляется только по реально затронутым занятиям
- текст уведомления должен включать понятную причину отмены

Если блок частично или полностью пересекается с существующим block-диапазоном:

- backend должен корректно обрабатывать дубликаты и не плодить лишние одинаковые block-записи

## Acceptance Criteria

- Во frontend admin Mini App больше нет режима `Заявки`.
- В календаре администратора вместо него есть режим `Бронь`.
- Администратор может забронировать весь выбранный день.
- Администратор может забронировать период внутри выбранного дня.
- Если новый блок пересекается с существующими занятиями, интерфейс предлагает выбор стратегии обработки конфликта.
- При выборе `просто заблокировать время` пересекающиеся занятия сохраняются, но новые записи в этот диапазон невозможны.
- При выборе `заблокировать и отменить занятия с уведомлением` пересекающиеся занятия отменяются, а ученики получают уведомление.
- Администратор может выбрать шаблон причины отмены или ввести причину вручную.
- После создания блоки отображаются в интерфейсе как интервалы на выбранную дату.
- Пользовательские свободные слоты и админские free slots больше не включают заблокированное время.
- Существующие записи не удаляются без явного выбора сценария отмены.
- Удаление блока из Mini App снова открывает соответствующее время для выбора, если нет других ограничений.
- Согласование заявок продолжает работать через Telegram-бот без участия Mini App.

- Выбрать сценарий `заблокировать и отменить занятия с уведомлением` и убедиться, что затронутые занятия отменились, а уведомления были отправлены.

- Проверить `/api/admin/schedule/day?date=...` и убедиться, что блоки отображаются как интервалы.
- Удалить бронь и убедиться, что соответствующие свободные слоты снова появляются.
- Проверить, что pending approvals по-прежнему обрабатываются в Telegram-боте.

## Rollback / Safety

- Если новый UI брони окажется нестабилен, можно временно скрыть frontend-режим `Бронь`, не удаляя backend-логику block-записей.
- Если возникнут ошибки в period block logic, можно оставить только full-day block как временный fallback.
- Если сценарий отмены с уведомлением окажется нестабилен, можно временно оставить только стратегию `block_only`.
- После релиза нужно вручную проверить день с уже существующими занятиями и день без занятий.

## Заметки

- Для этой задачи лучше не опираться на текущий special case full-day block через запись `00:00`, а постепенно привести full-day и period block к одной модели.
- Если в ходе реализации выяснится, что текущие функции `viewing_recordings_day_db` или расчёт свободных слотов завязаны на старый full-day special case сильнее ожидаемого, нужно будет вынести это в отдельный follow-up task или ADR.
