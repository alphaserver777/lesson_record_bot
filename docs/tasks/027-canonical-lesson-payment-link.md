# Task: canonical-lesson-payment-link

## Проверка Контекста Перед Работой

Перед реализацией перечитаны `WORKFLOW.md`, `constitution.md`,
`architecture.md`, `devplan.md`, `DEPLOYMENT.md`, ADR-002 и задача 014.

## Status

Done — deployed as release `5759a9a` on 17 August 2026.

## Контекст

Финансовое решение по занятию хранится в `payments`, но связывается с записью
только неявным набором `telegram_id + дата + час + минута`. После переноса,
повторного создания регулярного занятия или восстановления runtime одна и та
же операция может перестать находиться экраном «Незакрытые занятия».

## Цель

Сделать `record_dates.id` постоянным идентификатором проведённого занятия и
связать с ним единственное финансовое решение, сохранив чтение legacy-данных.

## Scope

В scope:

- nullable FK `payments.lesson_id → record_dates.id`;
- безопасный backfill существующих оплат;
- материализация регулярного занятия перед финансовым закрытием;
- поиск финансового решения сначала по `lesson_id`, затем по legacy-ключу;
- сохранение связи при переносе занятия;
- API/frontend-передача `lesson_id`;
- проверка целостности при старте и тесты ключевых сценариев.

Вне scope:

- удаление legacy-полей даты и времени из `payments`;
- изменение бухгалтерской модели предоплат;
- переписывание расписания и регулярных шаблонов.

## Ограничения

- миграция аддитивная и совместима со старыми клиентами API;
- предоплаты и платежи без конкретного занятия остаются с `lesson_id = NULL`;
- старые финансовые строки не удаляются;
- при нескольких legacy-решениях к занятию привязывается последнее, остальные
  сохраняются как история без `lesson_id`.

## Текущее состояние

- `Payment` не имеет FK на занятие;
- `find_payment()` ищет только по Telegram ID и времени;
- синтетическое регулярное занятие может не иметь строки в `record_dates`;
- перенос меняет `record_dates`, но не координаты связанного платежа.

## Предлагаемое изменение

1. Добавить `payments.lesson_id` с `ON DELETE SET NULL` и уникальным индексом.
2. Восстановить удалённые legacy-occurrence из финансовой истории и связать
   точным временным совпадением последнее решение каждого занятия.
3. Перед закрытием получать или материализовывать каноническое занятие.
4. Создавать не более одного финансового решения на `lesson_id`.
5. При переносе сохранять FK и обновлять snapshot-поля платежа.
6. Оставить временной поиск только как fallback для старых строк.

## Затронутые области

- `database/models.py`, `database/transactions.py`;
- схемы и routes финансов API;
- экран управления финансами Mini App;
- PostgreSQL schema и startup migration;
- архитектурная документация.

## Acceptance Criteria

- оплаченное занятие не появляется в незакрытых после рестарта;
- перенос оплаченного занятия не теряет финансовое решение;
- повторное закрытие одного `lesson_id` отклоняется;
- синтетическая регулярная запись получает постоянный ID до закрытия;
- старые оплаты и предоплаты не теряются.

## Verification

- тест backfill и уникальной связи;
- тест закрытия регулярного занятия и повторного поиска после новой DB session;
- тест переноса связанного занятия;
- сборка frontend;
- production backup, schema check, health-check API и бота.

## Rollback / Safety

- до deploy создать PostgreSQL dump;
- код можно откатить без удаления nullable-колонки;
- при полном rollback удалить только индекс/FK/колонку после отдельного dump;
- после deploy контролировать конфликты `uq_payments_lesson_id` и список
  незакрытых занятий.

## Заметки

Удаление legacy snapshot-полей возможно только отдельной задачей после периода
совместимости.

## Production verification

- перед миграцией создан и проверен PostgreSQL backup;
- после backfill: `694` финансовых строк, `645` текущих решений связаны с
  каноническими уроками, `0` идентифицируемых уроков без связи;
- контрольный финансовый отпечаток до и после рестарта одинаков:
  `694 / 1 179 650 ₽ / paid=457 / canceled=236 / linked=645`;
- API и bot одновременно перезапущены, оба вернулись в `healthy`, startup log
  не содержит deadlock или DB error;
- legacy miniapp/API на Germany2 остановлены, старый `/miniapp` перенаправляет
  в `https://crm.professorit.ru/cabinet/`, `/miniapi/*` возвращает `410`;
- Telegram callback получил версию runtime, поэтому кнопка из старой SQLite-БД
  больше не может обработать одноимённый numeric ID в PostgreSQL.
