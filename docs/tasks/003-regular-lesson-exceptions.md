## Контекст

Сейчас регулярные занятия задаются через `RegularLesson` как шаблон по дню недели и времени. Разовая отмена одного занятия из регулярной серии реализована через вспомогательные записи в `record_dates` с `kind="allow"` или через block-like механику.

Это создаёт несколько проблем:

- доменная модель становится неочевидной
- `regular`, `single`, `block`, `allow` и разовые исключения смешаны в одной таблице
- логика расчёта свободных слотов и отображения расписания вынуждена учитывать неявные маркеры
- разовая отмена регулярки выглядит как технический обходной путь, а не как отдельная бизнес-сущность

Целевое поведение должно быть таким:

- регулярка остаётся шаблоном повторения
- разовая отмена конкретной даты хранится как отдельное исключение
- после такой отмены слот на выбранную дату становится свободным
- в этот слот можно создать разовую запись
- со следующей недели регулярка продолжает работать без побочных эффектов

## Цель

Радикально, но безопасно перевести модель разовой отмены регулярных занятий на отдельную таблицу исключений, сохранив возможность отката и backup данных.

## Scope

В scope:

- создать новую вспомогательную таблицу исключений для регулярных занятий
- перевести сценарий разовой отмены регулярного занятия на эту таблицу
- обновить расчёт свободных слотов, чтобы исключение делало слот свободным на конкретную дату
- обновить отображение расписания и day view, чтобы исключение корректно скрывало регулярку на нужную дату
- сохранить возможность разовой записи в освобождённый слот
- подготовить безопасный backup данных перед изменением схемы
- подготовить rollback path на случай проблем

Вне scope:

- переработка модели block/admin reservation
- миграция SQLite на PostgreSQL
- полный рефакторинг всех календарных потоков за один шаг
- автоматическая миграционная система уровня Alembic
- изменение пользовательского UX вне сценария разовой отмены регулярки

## Ограничения

- Нельзя ломать существующие single bookings.
- Нельзя ломать admin blocks и бронь периода.
- Нельзя терять текущие данные БД при изменении схемы.
- Перед любыми schema changes должен быть сделан backup production БД на `Germany2`.
- Rollback должен быть реалистичным и понятным, а не декларативным.
- Переход должен быть инкрементальным: сначала новая модель поддерживается вместе со старой, потом старая логика отключается.

## Текущее состояние

- Регулярки хранятся в `regular_lessons`.
- Разовая отмена регулярки сейчас реализована через `allow`-механику.
- Регулярные занятия разворачиваются вперёд на 30 дней.
- При расчёте доступности слотов регулярки учитываются напрямую, без явной модели исключений.

## Предлагаемое изменение

### 1. Новая таблица

Добавить новую таблицу, например:

- `regular_lesson_exceptions`

Поля первой версии:

- `id`
- `regular_lesson_id`
- `exception_date`
- `action`
- `note`
- `created_at`

Минимально необходимое действие для старта:

- `skip`

Смысл:

- `RegularLesson` хранит только правило повторения
- `regular_lesson_exceptions` хранит только исключения на конкретные даты

### 2. Новая доменная логика

При разовой отмене регулярки:

- не создаётся `allow`
- не создаётся `block` как способ “не дать регулярке восстановиться”
- создаётся запись `skip` в `regular_lesson_exceptions`

При расчёте расписания на конкретную дату:

- если есть регулярка на этот weekday/time
- и есть `skip` на эту дату
- регулярка на этот день не считается занятой

Это делает слот свободным для single booking.

### 3. Совместимость на переходный период

На время миграции:

- новая логика исключений должна поддерживаться первой
- старая `allow`-логика не должна быть мгновенно удалена без проверки данных
- существующие старые `allow`-слоты нужно либо:
  - учесть как legacy-state
  - либо подготовить явный data migration plan

### 4. Backup и rollback

Перед реализацией schema change в production:

- сделать backup production БД на `Germany2`
- сохранить backup с timestamp и понятным именем
- зафиксировать путь backup в deployment docs или task notes

Rollback должен включать:

- откат к backup БД
- возврат на предыдущий commit
- пересборку production containers

## Acceptance Criteria

- Появляется отдельная таблица исключений для регулярных занятий.
- Разовая отмена регулярного занятия больше не требует `allow` как основной модели.
- После разовой отмены конкретный слот на этой дате становится свободным.
- В этот слот можно создать single booking.
- На следующей неделе регулярка продолжает работать по прежнему расписанию.
- Существующие single bookings и admin blocks продолжают работать.
- Перед production schema change сделан backup БД.
- Есть понятный rollback path.
