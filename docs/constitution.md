# Конституция Lesson Record Bot

## Назначение

Этот репозиторий содержит систему записи на занятия:
- Telegram-бот для взаимодействия с пользователями и администраторами
- FastAPI backend для Telegram Mini App
- React/Vite frontend для Mini App
- слой хранения данных и логики расписания на базе PostgreSQL

## Инженерные правила

1. Любое изменение логики записи, расписания или согласования должно явно определять source of truth и не должно дублировать правила между bot handlers и Web API.
2. Любая новая переменная окружения должна быть задокументирована в соответствующей задаче или ADR до merge.
3. Любой новый API route или изменение формы ответа должно иметь явную request/response validation.
4. Любое изменение схемы БД должно быть обратимым или иметь документированный rollback plan.
5. Пользовательские и административные сценарии не должны терять текущую рабочую функциональность, если только задача явно не выводит legacy-flow из эксплуатации.
6. Каждая задача должна содержать шаги verification; без них реализация не считается завершённой.

## Базовый процесс поставки изменений

1. Сначала создать или обновить task spec в `docs/tasks/`.
2. Обновить архитектурные заметки или ADR, если изменение влияет на границы системы или долгосрочные решения.
3. Реализовать минимально достаточное изменение.
4. Выполнить verification из задачи.
5. Явно зафиксировать follow-up, а не оставлять его скрытым в коде.

## Контроль качества

- Python-код должен корректно импортироваться.
- Mini App должен успешно собираться.
- Изменения в потоках записи и расписания должны сопровождаться ручным smoke-сценарием.
- Изменения, влияющие на production, должны быть отражены в `docs/devplan.md` или ADR.
